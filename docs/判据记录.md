## 批 2b —— 软关键字 18 词接线（2026-10-10）

**改动面**：`JavacParser.java`（由 `tools\接线软关键字.ps1` 应用：**助手 1 段 + 36 处替换**，每处带命中次数断言、幂等可重跑）+ 生成物 `ZhKeywords.SOFT` 首次被消费。上游树累计改动 4 个文件（另见批 2a）。

**原理（一句话）**：英文软关键字在 javac 里**不是词法层的**，而是解析层按位置用 `token.name() == names.X` 判定 ⇒ 中文软拼写**不能挂词法表**（挂了就会占掉标识符空间），只能在每个"期待软关键字"的位置一并接受。`isSoft(名, 英文名)` 先做恒等比较 ⇒ **英文行为完全不变**；其它位置仍是普通标识符 ⇒ `整数 记录 = 1;` 照旧合法，且 AST/字节码**保留中文原名**。

**18 词全部接线**：`自动 产出 记录 密封 许可 符合 模块 开放 开放包 依赖 传递 导出 指向 使用 提供 伴随 非密封 值类`

### 本轮修掉的两个**真 bug**（都不是判据用例的错）

1. **`non-sealed` 的 token 消费是硬编码的**：英文是三 token（`non` `-` `sealed`），所以 javac 在**修饰符位**（原 3626 行）与**局部类位**（原 3005 行）都写死了"多消费两个 token"。中文 `非密封` 只有一个 token ⇒ 多吃了 `类型 圆`，报：
   ```
   错误: 需要类、接口、批注类型、枚举、记录、方法或字段
   非密封 类型 圆 实现 形状 { }
   ```
   **修**：按形式决定消费几个 token（中文形式交给循环末尾的 `nextToken()`）。
2. **守卫口径过宽**：字符串口径会把"补丁注释里为解释而写出的关键字拼写"（我自己的注释里写了 `非密封`、`整数 记录 = 1;`）判成冲突 ⇒ 升级为**标识符精算**：先剥掉 `//` 注释、`/* */`（同行）块注释、字符串/字符字面量，再找拼写；同时把 `tests/` 移出扫描范围（用例天然必须写这些拼写，改由"用我们自己编出的 JDK 编过 + 中英对拍"把关）。

## jtreg 在中文 Windows 上的环境坑（目标 ⑦ 的关键发现，2026-10-10，目标轮 3/30）

**现象**：更大范围回归（parser/records/sealed/patterns/valhalla/modules/diags）首跑 **97 个测试红**，
失败长这样：

```
comparison failed, index 4, (4 warnings:4 个警告)
AssertionError: Incorrect errors, expected: [... 2 errors], actual: [... 2 个错误]
Output does not match reference file: MissingClosingBrace.out, line 2
（参考文件：MissingClosingBrace.java:12:5: compiler.err.illegal.start.of.expr / 1 error
  实际输出：MissingClosingBrace.java:12:5: compiler.err.illegal.start.of.expr / 1 个错误）
```

**定性**：差的**只有计数行**（`N errors` vs `N 个错误`），而计数行来自 `compiler.misc.count.*`，
**我们的表一个字都没动它**（`grep count|个错误` 在两张表里命中 0）。根因是：
Windows 上 Java 的默认 locale 取自**系统区域设置**，`LC_ALL`/`LANG` 完全无效 ⇒ jtreg 在中文 Windows 上
跑这些对拍英文参考文件的测试必然假失败。

**三个通道才够（实测，缺一即红）**

| 通道 | 作用对象 | make 变量 → jtreg 选项 | 出处 |
|---|---|---|---|
| ① | **agent VM**（jtreg 跑 `@compile` 动作的 JVM，计数行在这里产生） | `TEST_OPTS_VM_OPTIONS` → `-vmoption:` | RunTests.gmk:211 |
| ② | **测试 VM**（测试进程内用 JavaCompiler API 并断言英文） | `TEST_OPTS_JAVA_OPTIONS` → `-javaoption:` | RunTests.gmk:212 / 965 |
| ③ | **jtreg 自身 JVM** | `JTREG_LAUNCHER_OPTIONS` | RunTests.gmk:918 / 1076 |

外加环境变量 `JAVA_TOOL_OPTIONS` 兜底（覆盖测试自己 spawn 的 java 子进程）。

**踩坑记录**：
1. 只加 `JAVA_TOOL_OPTIONS` → **无效**（jtreg 给测试/agent VM 用受控环境，`JAVA_TOOL_OPTIONS` 到不了；RunTests.gmk:144 用 `-e:` 才传得进去）。
2. 只加 `TEST_OPTS_JAVA_OPTIONS` → **sealed 组转绿、`.out` 对拍组仍红**（因为 `-javaoption:` 管的是测试 VM，不是跑 `@compile` 的 agent VM）。
3. 只有再加 `TEST_OPTS_VM_OPTIONS` → **全绿**（`Test summary / TEST SUCCESS`）。

**判据**
```
加 TEST_OPTS_VM_OPTIONS 后复跑刚才还红的三个：
  Passed: tools/javac/parser/MissingClosingBrace.java     Test results: passed: 1
  Passed: tools/javac/parser/T4881269.java                Test results: passed: 1
  Passed: tools/javac/parser/ErroneousParameters.java      Test results: passed: 1
  Test summary / TEST SUCCESS     make test 退出码 0（51 秒）
```
⇒ 上游测试在中文 Windows 上要这样跑才准；`tools\跑测试.ps1` 已把三通道设成**默认**（`-语言 en`）。

**纪律教训**：遇到"回归红"，先看**真实差异**（我读了 `.jtr` 里的 `direct:` 段，拿到 `1 \u4e2a\u9519\u8bef`），
再对照"我们的表动过没有"（`grep count` 命中 0），最后用**只改一个变量的对照实验**定性 —— 三步都做完才敢说"不是我们的 bug"。

## 批 1 补完：结构性关键字的覆盖（2026-10-10，目标轮 6/30）

**上一轮遗留**：只有 `TokenKind` 带 `Tag.NAMED` 的中文硬关键字会走专属消息；结构性关键字

```java
private String zhSpelling(Token token) {
    if (token.kind.tag == Token.Tag.NAMED) {          // 布尔/整数/真值/空值…
        return ZhKeywords.hardKeyword(token.name().toString());
    }
    var sourceFile = log.currentSourceFile();         // 结构性关键字：按位置回读
    CharSequence content = sourceFile.getCharContent(false);
    return ZhKeywords.hardKeyword(content.subSequence(token.pos, token.endPos).toString());
}
```

# 路线转折：从「别名层」转到「汉语平行库」（2026-10-10，目标轮 14-15）

## 用户裁定的架构（我先前理解错了）

> **L4（本体）**：复制原库，在副本上改，**库名/包名/类名/方法名真名就是汉语**。
> **兼容层（加在 L4 之上）**：用 L3 那套"查不到就换名重查"的机制，**反过来**加英文用法
> （英文拼写 → 中文真名），使"原来的英文用法尽可能都能用"。

即：**汉语是本体，英文是别名**。（我先前做的 L3 是"原库不动、编译器认中文名"，方向相反。）

用户另外三点裁定：
- 副本**自成体系**（不复用原库接口/父类），因此**成员名可以全用中文真名**；
- 英文兼容层要**尽可能覆盖原来的英文用法**；
- 暂**不要求交付物**，先把路走通。

## 技术勘测（全部实测，不是推测）

| 事项 | 实测结果 |
|---|---|
| 模块名 `java.基础`、包名 `java.工具.函数`、中文类名/方法名 | ✅ **javac 全通**（编译退出码 0）；产物 `函数.class`，`javap` 显示 `乙 应用(甲)`、`函数<甲,乙> 然后(...)` ⇒ **副本真名就是中文** |
| 普通 javac 编 `package java.util.function;` | ✗ `错误: 程序包已存在于另一个模块中: java.base`（该包属于 java.base） |
| `javac --patch-module java.base=…` | ✅ 通过（JDK 自己的构建就这么编 java.base） |
| 把 `java.*` 的 class 放 classpath 运行 | ✗ 不认（app loader 不会去那里找 `java.*` 包） |
| 从 module-path 加载模块 `java.基础` | ✗ `LayerInstantiationException: Class loader (instance of): 'app' tried to define prohibited package name: java.工具.函数` |

规则统一为：**`java/` 后紧跟的那一段以非 ASCII 开头 ⇒ 放行；ASCII 段一律继续禁止。**

2. **删掉功能 ≠ 删掉该功能的判据就够了**：`verify.ps1` 里那些"检查文件存在"的条目、
   `跑批4` 里那些引用夹具的断言，都不会自己消失；不逐处摘掉就是**红着的自检**。
3. **回退安全放宽必须配一条"它确实不再放行"的判据**（K4-4）。只回退代码、不加反向断言，
   下次谁再引入同类放宽都不会被发现。
4. 改动跨越 **C++ / Java / PowerShell / Markdown** 四层时，**只有重建镜像才算验证**；
   拿旧镜像跑判据会得到"全绿"的假象（本轮就这么绿过一次）。
